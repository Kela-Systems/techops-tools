Arrow Lake operator stations: Mesa fix

TechOps support runbook · TEC-880 · tool: techops-tools/operator_station/arrow-lake-mesa/arrow-lake-mesa.sh · October 2026

In one paragraph. Operator stations with an Intel Arrow Lake GPU (PCI id 8086:7d67) run our Ubuntu 22.04 image with Mesa 23.2.1, which does not support that GPU. Chrome and the desktop then draw everything on the CPU. The station runs close to its limit even when idle, and under load the screens freeze or lag and video stalls. Rebooting does not help. Installing a newer Mesa (25.x) moves the drawing back to the GPU. It needs no hardware change and no Ubuntu upgrade, and can be rolled back.

1. Is this station affected?

Signs on a station that needs the fix:

  • Frozen or slow screens, stuck video, or the kiosk relaunching, often on busy, multi-screen stations.
  • lspci shows 8086:7d67, and Mesa is 23.2.1.
  • The desktop compositor (gnome-shell) uses ~70–80% of a CPU core, and CPU pressure is 4–18% at idle.

2. Before you start

  • Coordinate with the site. The final step reboots the station: all its screens go dark for ~2–3 minutes. Pick a quiet moment and tell the position.
  • You need SSH to KelaAdmin@<site>-operator (over Tailscale) and the KelaAdmin password (1Password). The tool never stores or passes the password; ssh/sudo prompt for it.
  • Get the tool: git clone / git pull the techops-tools repo, then cd operator_station/arrow-lake-mesa. It runs on macOS or Linux (bash, ssh).

3. The fix: three commands

Step 1: snapshot before (read-only, optional but recommended)

./arrow-lake-mesa.sh check kela-fob-08-operator

Prints the GPU, Mesa version, CPU pressure, compositor/Xorg/Chrome CPU and Chrome's own GPU report, and saves it under ./arrow-lake-reports/. The last line tells you whether the station is a candidate.

Step 2: apply (installs Mesa, then asks before rebooting)

./arrow-lake-mesa.sh apply kela-fob-08-operator
  1. Saves a before snapshot automatically.
  2. Refuses unless the GPU is 8086:7d67, the OS is 22.04 and the kernel driver is i915. It does nothing if the station is already fixed.
  3. Asks for the KelaAdmin password (sudo), adds ppa:kisak/turtle and upgrades the Mesa packages. This runs non-interactively, so the "Daemons using outdated libraries" dialog does not appear.
  4. Asks "Reboot now? [y/N]". Answer y when the site is ready.

Step 3: verify (~5 minutes after the reboot)

./arrow-lake-mesa.sh verify kela-fob-08-operator

Takes an after snapshot, prints it next to the before, and checks:

CheckPass when
Mesaversion contains kisak (e.g. 25.0.7~kisak3~j)
Chrome renderercontains Mesa Intel(R) Graphics (ARL) (not llvmpipe / SwiftShader)
GPU compositingenabled
Desktop compositor (gnome-shell)under 20% CPU (was ~70–80%)
Kioskat least one C2 tab is open

It ends with RESULT: PASS or RESULT: FAIL. If the station has been up under 5 minutes it says so; run verify again a few minutes later.

Expected limit: the drawing load disappears, but video decoding stays on the CPU, because there is no Arrow Lake video driver for 22.04. That is why Chrome's own CPU barely changes on busy multi-screen stations. Hardware video decode comes with the 24.04 image (TEC-910). On the heaviest stations, also reduce load where the site agrees: force 1080p (KIOSK_PREFERRED_RESOLUTION), use the 2D map, keep one screen on camera, and disconnect unused screens.

5. If something goes wrong: rollback

./arrow-lake-mesa.sh rollback kela-fob-08-operator

Removes the PPA, returns to Ubuntu's own Mesa 23.2.1 with ppa-purge, and asks before rebooting. Use it if the screens come back black, the kiosk does not start, or verify fails twice.

6. Doing it by hand (if the tool can't be used)

The same steps, run from your laptop. Each asks for the KelaAdmin password.

Before: read-only metrics

ssh KelaAdmin@<station> 'lspci -nn | grep -i vga; lspci -k -s 00:02.0 | grep "driver in use"; dpkg-query -W libgl1-mesa-dri; head -1 /proc/pressure/cpu; uptime; top -b -n 2 -d 5 -w 200 | awk "/^top -/{n++} n==2" | grep -E "gnome-shell|Xorg|chrome" | head'

Install

ssh -t KelaAdmin@<station> 'sudo add-apt-repository -y ppa:kisak/turtle && sudo apt-get update -q && sudo env DEBIAN_FRONTEND=noninteractive NEEDRESTART_MODE=l apt-get install -y -q --only-upgrade libgl1-mesa-dri libglx-mesa0 libegl-mesa0 libgbm1 mesa-vulkan-drivers'

One command on one line. Copy it whole.

If a "Daemons using outdated libraries" dialog still appears: leave only fwupd ticked and press Enter on <Ok>. Do not tick gdm3 (it would log the operator out mid-install). A line saying packagekit.service is masked is harmless.

Reboot (coordinate first)

ssh -t KelaAdmin@<station> 'sudo reboot'

After (~5 min): same read-only metrics as "Before". Success means the new Mesa version, gnome-shell well under 20%, and Xorg a few percent.

Chrome's own view: on the station screen (AnyDesk) open chrome://gpu. Compositing and Rasterization should say Hardware accelerated, and the GL renderer should be "Mesa Intel(R) Graphics (ARL)".

Rollback

ssh -t KelaAdmin@<station> 'sudo env DEBIAN_FRONTEND=noninteractive NEEDRESTART_MODE=l apt-get install -y -q ppa-purge && sudo env DEBIAN_FRONTEND=noninteractive NEEDRESTART_MODE=l ppa-purge -y ppa:kisak/turtle'

Then reboot, after telling the site, with the same command as above: ssh -t KelaAdmin@<station> 'sudo reboot'.

7. Troubleshooting

SymptomWhat to do
apply refuses: GPU not 7d67Not an Arrow Lake station. This fix does not apply; follow the operator-station runbook.
apply refuses: driver not i915The kernel isn't driving the GPU. Don't apply; escalate to TechOps (it may need i915.force_probe=7d67).
Screens black after the rebootWait 5 minutes. If still black: rollback, then escalate.
verify can't read Chrome's GPU reportThe kiosk is not up yet, or Chrome's DevTools port is off. Wait and re-run, or check chrome://gpu on screen.
Video tiles drop all at once and C2 shows its connection error, then recoversA different problem: the station loses its connection to the server (network/cable/switch). Mesa does not fix it. Report it separately with the time it happened.
Still slow on a 3–4 screen station after PASSExpected video-decode load (see §4). Apply the load reductions and report the station.

8. After the fix

  • Add a note to the ticket: station, time, Mesa version, and the verify result (paste the output or attach the files from arrow-lake-reports/).
  • The incident-agent's station check still flags "Arrow Lake, no GPU driver" by GPU model alone, until it learns to read the Mesa version. Ignore that flag on fixed stations.
  • Fleet tracking: TEC-880 (this fix), TEC-910 (24.04 image, where video decode also gets fixed).
